# Production Dispatch Instance Design

## Overview

This change defines production dispatch from an external `order_item` contract into frozen production instances.

It is OpenSpec-only. It must not create code, migration files, API implementations, frontend pages, or database tables in this change.

The design follows the project rule:

```text
Configuration stage is flexible.
Execution stage is frozen.
Template can change.
Instance cannot be disturbed.
```

## Production Dispatch Flow

1. Production manager opens production configuration for an `order_item`.
2. Production module reads `order_item` through an order-item read contract or temporary mock/demo adapter.
3. Production module queries enabled and non-deleted route template options by `order_item.product_type`.
4. Production manager selects a route template.
5. Production module reads the selected route template and active enabled step templates.
6. Frontend creates a request-scoped or frontend-held editable pre-dispatch configuration from the template.
7. Production manager adjusts steps before dispatch.
8. Production manager confirms dispatch.
9. Dispatch service validates the `order_item`, template, and configured step list.
10. Dispatch service creates one `production_route_instance`.
11. Dispatch service creates ordered `production_step_instance` records from the configured snapshot.
12. Dispatch service marks the route instance as `frozen = true`.
13. Dispatch service marks step instances as frozen or enforces structure through `route_instance.frozen`.
14. Dispatch service writes only production fields back to `order_item`.
15. Order-line pages can query the production summary API.

## Data Flow

```text
order_item
→ process_route_template
→ process_step_template
→ dispatch draft/config
→ production_route_instance
→ production_step_instance
```

### `order_item` as External Shared Contract

The production line consumes `order_item` as an external contract owned by the customer/order line.

Minimum read fields:

```text
id
order_id
item_name
product_type
quantity
status
production_status
production_progress
production_route_instance_id
```

The first implementation stage uses production-owned ports:

```text
OrderItemReadPort
OrderItemProductionPort
```

The dev/test implementation may use:

```text
mock/demo order_item data
minimal production-field write-back adapter
```

The dev/test adapter lives inside the backend production module. It can only provide:

```text
read minimum order_item fields needed for dispatch
write order_item.production_status
write order_item.production_progress
write order_item.production_route_instance_id
```

It must not provide:

```text
order creation
order amount
customer data
quotation data
product specification ownership
order core status ownership
CRM logic
public pool logic
contribution logic
```

The implementation must mark mock/demo integration:

```text
TODO: replace with customer-line order_item contract
```

After Cursor order-line implementation is available, production should replace the mock/demo adapter with the real customer-line `order_item` query contract or agreed table read.

## Dispatch Draft / Configuration Model

The pre-dispatch configuration model represents editable production steps before freeze.

Confirmed MVP approach:

```text
Use request-scoped or frontend-held configuration.
Do not persist dispatch drafts.
Do not create dispatch_draft tables.
Frontend generates editable steps from the selected template.
Frontend submits the full configuration once when confirming dispatch.
Backend persists only production_route_instance and production_step_instance after confirm dispatch.
```

Rejected for MVP:

```text
persisted dispatch draft tables
draft lifecycle cleanup
partial draft save APIs
```

Reasoning:

- It avoids introducing draft lifecycle cleanup too early.
- It keeps the MVP focused on the dispatch/freeze invariant.
- It still supports full pre-dispatch editing before confirm because the full config is submitted at dispatch time.
- It avoids creating another table before the customer-line order contract is stable.

Draft/config step fields:

```text
temp_id or client_step_id
source_step_template_id nullable
step_name
step_order
assigned_role
assigned_user_id nullable
photo_required
remark_required
mobile_enabled
estimated_hours nullable
operation_instruction nullable
```

Concrete assignee rule:

- `assigned_role` is required for each dispatch step.
- `assigned_user_id` is optional and nullable in MVP.
- The first version does not force concrete worker assignment.
- If a page supports selecting a responsible person, it may submit `assigned_user_id`.
- If a page does not support responsible person selection, steps are generated by `assigned_role` only.
- Do not force template-level employee binding.

## State Machines

### `order_item.production_status`

Suggested states:

```text
NOT_DISPATCHED
DISPATCHED
IN_PROGRESS
COMPLETED
PAUSED
```

This change only needs dispatch-stage behavior:

```text
NOT_DISPATCHED → DISPATCHED
```

Later worker execution may update:

```text
DISPATCHED → IN_PROGRESS → COMPLETED
```

Out of scope for this change:

```text
worker start
worker complete
pause handling
```

### `production_route_instance.status`

Suggested states:

```text
DISPATCHED
IN_PROGRESS
COMPLETED
PAUSED
```

Initial status after dispatch:

```text
DISPATCHED
```

### `production_step_instance.status`

Suggested states:

```text
PENDING
IN_PROGRESS
COMPLETED
BLOCKED
```

Initial status after dispatch:

```text
PENDING
```

This change only creates step instances with initial status. It does not implement execution transitions.

## Freeze Rules

After confirm dispatch:

```text
production_route_instance.frozen = true
```

Step freeze may be represented by:

```text
production_step_instance.frozen = true
```

or enforced by:

```text
production_route_instance.frozen = true
```

Frozen structure means the system must reject:

- adding production step instances
- deleting production step instances
- changing step order
- changing step name as process structure
- changing assigned role as process structure
- changing photo requirement
- changing remark requirement
- changing mobile execution flag
- skipping steps
- rework
- adding execution-time steps

Allowed later execution updates are explicitly separate:

- step status
- started_at
- completed_at
- execution remark or check-in remark
- execution photo check-in through a later change

This change does not implement those later execution updates.

## Template Snapshot Copy Rules

Production instances must copy template and configuration values into snapshot fields.

Route snapshot examples:

```text
source_route_template_id
source_route_template_version
route_code_snapshot
route_name_snapshot
product_type_snapshot
route_description_snapshot
```

Step snapshot examples:

```text
source_step_template_id
step_code_snapshot
step_name
step_order
assigned_role
assigned_user_id
photo_required
remark_required
mobile_enabled
estimated_hours
operation_instruction
```

Execution must use `production_route_instance` and `production_step_instance` as the source of truth.

Execution must not directly reference `process_route_template` or `process_step_template` as live execution source.

If the source template is edited after dispatch, existing production instances must not change.

## Idempotency Rules

Default MVP rule:

```text
One active order_item can be dispatched at most once.
```

If an `order_item` already has an active `production_route_instance`, dispatch must return a conflict business error and must not create another instance.

Suggested error:

```text
ORDER_ITEM_ALREADY_DISPATCHED
```

MVP does not implement complex idempotent replay.

`idempotency_key` may exist as a reserved field, but it must not change the duplicate-dispatch behavior:

```text
same order_item already dispatched
→ ORDER_ITEM_ALREADY_DISPATCHED
```

Future idempotent replay, if needed, requires a separate design update.

## Exception Scenarios

### `order_item` does not exist

Return a business error such as:

```text
ORDER_ITEM_NOT_FOUND
```

Do not create production instances.

### `order_item` already dispatched

Return:

```text
ORDER_ITEM_ALREADY_DISPATCHED
```

Do not create duplicate route or step instances.

### Template does not exist, is disabled, or is deleted

Return:

```text
ROUTE_TEMPLATE_NOT_AVAILABLE
```

Do not create dispatch config from unavailable templates.

### Template has no copyable enabled steps

Return:

```text
ROUTE_TEMPLATE_HAS_NO_ENABLED_STEPS
```

Do not allow dispatch with an empty copied template.

### Dispatch configuration has no steps

Return:

```text
DISPATCH_STEPS_REQUIRED
```

Do not create an empty production route instance.

### Frozen structure modification attempted

Return:

```text
PRODUCTION_ROUTE_FROZEN
```

Do not modify production route or step structure.
