# Production Work Order Proposal

## Why

The current production chain goes directly from customer-line `order_item` to `production_route_instance`.

That is not enough for real non-standard manufacturing. An order item describes what the customer bought. A production work order describes what the production department must build, prepare, inspect, and hand over.

This change introduces the missing production-side document layer:

```text
order_item
-> production_work_order
-> production_route_instance
-> production_step_instance
```

The work order becomes the production department's internal instruction sheet. It carries schedule requirements, equipment or product configuration, technical configuration, production requirements, material needs, responsible people, and confirmation/signature fields.

Confirmed future main flow:

```text
order_item
-> production_work_order
-> production_route_instance
-> production_step_instance
```

After this OpenSpec is approved and later implementation starts, new production dispatch should be driven from `production_work_order`, not directly from `order_item`. This change does not refactor the existing `production-dispatch-instance` OpenSpec or existing dispatch capability. During the transition, the legacy `order_item -> production_route_instance` path may continue to exist until the implementation is moved step by step to the work order flow.

This change is OpenSpec-only. It must not create code, migrations, Controller APIs, frontend pages, inventory logic, file upload, photo check-in, worker apps, CRM, public pool, contribution, or order core logic.

## Goals

- Define `production_work_order` as a production-owned internal document.
- Define how to create a production work order from an existing customer-line `order_item`.
- Define the future production main flow as `order_item -> production_work_order -> production_route_instance -> production_step_instance`.
- Preserve the transition rule that this change does not refactor existing `production-dispatch-instance` behavior.
- Preserve order-line ownership:
  - production reads `order_item`
  - production does not create orders
  - production does not modify customer/order core fields
- Draft `production_work_order` fields:
  - work order number
  - `order_id`
  - `order_item_id`
  - optional `production_route_instance_id`
  - status
  - production instruction fields
  - technical configuration fields
  - production requirement fields
  - delivery and schedule fields
  - responsible person, handler, and production personnel fields
  - signature and confirmation fields
- Define work order statuses:
  - `DRAFT`
  - `RELEASED`
  - `IN_PROGRESS`
  - `COMPLETED`
  - `CANCELLED`
- Define active work order statuses as:
  - `DRAFT`
  - `RELEASED`
  - `IN_PROGRESS`
- Define non-active work order statuses as:
  - `COMPLETED`
  - `CANCELLED`
- Require one active `production_work_order` per `tenant_id + order_item_id` in MVP.
- Reject duplicate active work order creation with a business error instead of automatically reusing the existing work order.
- Define work order number format as `WO-{yyyyMMdd}-{dailySequence}`.
- Require tenant-unique work order numbers generated by daily tenant sequence.
- Draft `production_work_order_material` or material requirement child table fields.
- Keep material requirements as demand records only in this change.
- Prepare a future boundary for inventory readiness, shortage display, reservation, and stock deduction.
- Prepare a future boundary for nested and parallel process graphs.
- Define how a work order relates to `production_route_instance`, `production_step_instance`, and future check-in evidence.
- Define API shapes as drafts only.
- Define table shapes as drafts only.
- Define verifiable tasks and DoD for future implementation planning.

## Collaboration Boundaries

Codex owns the production line:

- production work orders
- production instruction fields
- production-side material requirement drafts
- production route instance relation
- production step relation
- future inventory/material-readiness boundary
- future process graph boundary

Cursor owns the customer/order line:

- CRM
- customer public pool
- contribution
- order creation
- order amount and quotation
- customer and contact data
- order item core fields such as product specification and quantity

Production may read `order_item` through a production-owned port. Production must not implement customer/order core logic.

Production must not modify:

```text
customer data
customer contact data
order amount
quotation data
product specification
product quantity
order custom fields
customer source
CRM state
public pool state
contribution account
contribution transaction
```

The production work order is a production-owned internal document. It may reference `order_id` and `order_item_id`, but it does not become the customer-line order source of truth.

## Risks

- If `order_item` continues to carry production instruction fields, customer/order ownership will become blurred and future Cursor/Codex work will conflict.
- If a work order is skipped and production route instances stay directly attached to order items, material readiness and production preparation will have no stable document anchor.
- During the transition, both the legacy direct dispatch path and the new work order path may exist; implementation must avoid duplicate dispatch semantics and make the new main flow explicit in UI/API naming.
- If material requirements are mixed with stock deduction too early, the MVP may accidentally implement inventory, purchase, supplier, or finance scope before the work order model is stable.
- If shortage is treated as blocking the whole work order, usable upstream steps may be delayed unnecessarily.
- If non-linear process graph design is mixed into this change, the scope will become too large and risk breaking the already implemented serial execution flow.
- If work order fields are too customer/order-like, production may accidentally mutate order core fields instead of recording production-side snapshots.
- If work order number generation is implemented without tenant/date sequence locking or retry, concurrent creation can produce duplicate numbers.
- If verification evidence is not required, OpenSpec-only work may be mistaken for implemented code.
